Three bugs found during my code review, ranked by impact:

BUG 1 — device_state.py chip_src heuristic misclassifies Google catalog entries
The heuristic:
  chip_src = ('spec-sheet' if any(c.isdigit() for c in chip.split()[1:2] or [''])
              or '(' in chip else 'google-catalog')
Real Google catalog SoC values with digits in the second word:
  'Mediatek MT8768T'  -> classified as spec-sheet (WRONG, came from catalog)
  'QTI SM8650'        -> classified as spec-sheet (WRONG, came from catalog)
  'Samsung s5e9945'   -> classified as spec-sheet (WRONG, came from catalog)
  'Qualcomm SDM845'   -> classified as spec-sheet (WRONG, came from catalog)
Only 'Google Tensor G2/G3' (no digits in second word) correctly classifies as google-catalog.
This affects provenance/authority labeling for 4+ of 7 catalog SoC format families.
FIX: Track the source during ingestion rather than inferring it from the value string.

BUG 2 — UA mismatch between probe() and collectors
  common.py probe():        'Mozilla/5.0 (compatible; device-crawler/1.0)'
  collect_gsm_slugs.py:     Full Chrome UA string
  fota_modem.py:            'Kies2.0_FUS' (now banned, but still in code)
probe() tests reachability with our declared UA, but collect_gsm_slugs.py then fetches with a different UA. A site that returns 200 to our honest UA but 403s to Chrome (or vice versa) will produce a misleading probe() result. All non-banned collectors should use the same UA as probe().

BUG 3 — spl_src only tracks 'samsung-doc' or generic 'source'
device_state.py's spl_src does not implement the three-tier authority model from the caveats I sent (vendor-official > vendor-derived > community). It currently only distinguishes 'samsung-doc' vs 'source'. With TECNO, HMD, and potentially more vendor feeds now live, spl_src should carry the vendor name and authority tier so Rule 1 can do its job on collisions.
