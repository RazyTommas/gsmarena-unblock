THREE PROVENANCE RULES FOR COMMUNITY-SOURCED ASPL ROWS

These govern how device_state weights ASPL rows from different sources. They apply per-row, not per-source — a single source can produce rows at different authority and precision tiers.

RULE 1: SOURCE AUTHORITY TIER (per row)

  vendor-official  — From the OEM's own published security bulletin or API.
                     Samsung doc.samsungmobile.com, TECNO security.tecno.com,
                     HMD hmd.com/en_int/security-updates.
                     The vendor authored the value AND published it as a security
                     update record. Highest weight.

  vendor-derived   — Extracted from official firmware metadata (build.prop from OTA,
                     firmware manifest) where the OEM authored the ro.build.version.security_patch
                     value but did not publish it in bulletin format. The value is real
                     but the MAPPING (device → value) is ours, not the vendor's.
                     Middle weight.

  community        — From a community tracker, user-submitted database, or crowd-sourced
                     upload site. No vendor endorsement of the device→ASPL mapping.
                     iQOO, OnePlus, vivo rows from non-vendor sources carry this.
                     Lowest weight.

  RESOLUTION: If two rows cover the same (device, build), vendor-official wins over
  vendor-derived wins over community. A community row is used ONLY when no higher-authority
  row exists for that device. If vendor-official and community disagree on the ASPL for the
  same build, the community row is discarded, not averaged.

RULE 2: PRECISION GATING VIA DAY-OF-MONTH DISTRIBUTION (per source, verified once)

  Before ANY source's patch-level column is believed, run the day-of-month distribution check:

    dates = [parse(row.spl).day for row in source if row.spl]
    day_01_05_pct = sum(1 for d in dates if d in (1, 5)) / len(dates)

  - day_01_05_pct >= 0.95  →  genuine ASPL column, record at stated precision
  - day_01_05_pct < 0.95   →  REJECT THE ENTIRE COLUMN. It is a build/upload timestamp,
                                not a patch level. Do NOT downgrade to month — a scattered
                                distribution means the field is the wrong one entirely.

  This caught mifirm.net (upload timestamps), sammobile CP prose (build dates),
  and separated HMD's androidBulletinDate (100% day-01) from dateOfFirstLiveRelease
  (scattered) in the SAME JSON object. Three for three is a rule.

  A source that passes gets its precision recorded:
    date  (YYYY-MM-DD)  — Samsung (day-01/05), HMD (day-01)
    month (YYYY-MM)     — TECNO API titles say "2026-08" with no day

  Already implemented: month-precision never adjudicates within a month, and
  padding 2026-08 to 2026-08-01 is forbidden because it silently asserts a tier.

RULE 3: STALENESS MARKING (per source)

  Each source has a liveness date: the publication date of its most recent bulletin/record.

    fresh   — last bulletin within 90 days
    aging   — 90-180 days
    stale   — >180 days since last bulletin

  Stale rows are STORED, not discarded, but carry:
    stale: true
    stale_since: <date of last bulletin>

  The adjudicator treats stale rows as LOWER-BOUND assertions:
    "This device was at patch level X as of <stale_since>"
    NOT: "This device is currently at patch level X"

  This means a stale row still asserts OPEN against CVEs fixed BEFORE stale_since,
  but does NOT assert open against CVEs fixed after — the device may have updated
  through a channel we lost visibility into.

  Xiaomi is the canonical case: feed died 2025-02. Their 331 devices carry no ASPL
  rather than a 19-month-old one, because asserting "open against 19 months of CVEs"
  when we simply lost the feed is a claim about the vendor, not about the data.
  If a live source surfaces, it replaces the gap. If not, historical values are
  available under stale: true for anyone who wants lower-bound reasoning.

COMBINED EFFECT ON THE THREE VENDORS:

  iQOO   — source_authority=community, day-distribution verified before recording,
            stale_since checked per source. Used only when no vendor-official exists.
  OnePlus — same. security.oneplus.com exists but is JS-SPA with CAPTCHA, inaccessible
            to automated clients. No programmatic official source found.
  vivo    — same. No official security update page found at any tested URL.

  All three: if a vendor-official source surfaces later, it supersedes the community
  rows for overlapping devices without manual intervention — Rule 1 handles it.
