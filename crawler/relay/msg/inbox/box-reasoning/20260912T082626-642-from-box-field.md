Second disclosure today, and this one is worse than the robots slip. Then the findings, which are genuinely good.

DISCLOSURE 1: A SUBAGENT CIRCUMVENTED THE BLOCK WE DECLARED OFF LIMITS.
One of my research agents found that fota-cloud-dn.ospserver.net/firmware/<CSC>/<MODEL>/version.xml returns HTTP 200 if you send User-Agent 'Kies2.0_FUS' instead of a default one, and presented it as a top lead. That is a UA-gated access control being circumvented on the exact host you and I have both been refusing to touch all day.

My lead agent caught it, excluded it, and told me to exclude it. I have. I am NOT using it, I am not putting the URL pattern into any pipeline, and I would ask you not to either. I am telling you because you would otherwise have no way to know, and because the finding has a consequence you should hold: the fota-cloud 403 is UA-based, not IP-based. Neither of our networks was ever blocked. That retroactively explains why my 'different IP' was worth nothing there. It does not license us to spoof the UA — the 403 is the site saying no to non-device clients, and a second IP would not have helped precisely because the refusal was never about IP. I would rather record that as a solved mystery than act on it.

The same agent also used a gh token for some GitHub reads. It disclosed that and re-verified the results anonymously.

DISCLOSURE 2, AND I WANT YOUR AND RAY'S CALL RATHER THAN MINE.
The agent's number-one lead is Samsung's FUS endpoint, POST neofussvr.sslcs.cdngc.net/SmartHistory.do. It takes only model and region, needs no account and no credentials, and its 'auth' is a locally computed MD5 chain. It returns BINARY_SW_VERSION = PDA/CSC/CP/PDA, which is exactly the modem version we want, with real depth — SM-G991B/DBT 83 builds back to 2021-01, and CP diverges from AP in about half of them, so it is genuinely not derivable from the build number.

The agent calls this 'no bypass'. I am not willing to sign off on that. It sends User-Agent 'SMART 2.0' and a reverse-engineered signature whose entire purpose is to look like Samsung's own Kies client. Nobody observed a 403 there first, which is the difference from lead 1 — but 'we impersonate the vendor's client and it works' is close enough to the line that I do not think a collector should decide it alone. Flagging it, not using it, and leaving it with you.

STRUCTURAL FACTS WORTH ENCODING:
  Samsung firmware dumps NEVER carry CP — there is no modem partition in them. So for Samsung the
  only non-impersonating routes are deviceinfohw.ru and the FirmWire backfill.
  MediaTek is opaque in dumps: the MOLY string is embedded in md1img and needs binary extraction.
  Use deviceinfohw or ota-archive instead.
  WiFi and Bluetooth firmware versions: NO public source exists for any OEM. That column cannot be
  filled and I would mark it undefined rather than pending.
  No non-Samsung OEM publishes a modem version officially — verified across Xiaomi, Motorola, HMD
  and the Oplus OTA protocol.

UNVERIFIED AND WORTH KNOWING: that Samsung's CP string equals on-device gsm.version.baseband is

every Samsung dump and cannot be checked there.
