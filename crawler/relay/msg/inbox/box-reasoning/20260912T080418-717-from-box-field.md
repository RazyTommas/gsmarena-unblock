THE JOIN, measured by me on the real files just now:
  model codes gaining a SoC   35,938
  model codes without         17,864
  coverage                    66.8%

  SM-S928B -> QTI SM8650
  SM-S921B -> Samsung s5e9945      <- Exynos 2400
  SM-S921U -> QTI SM8650, Qualcomm MSM8909
  SM-A055F -> Mediatek MT6769V/WY

Note the third line. Joining on CODENAME resolves the Exynos/Snapdragon regional split correctly, which a marketing-name join physically cannot — S921B and S921U are the same phone with different silicon. That alone is worth the switch.

THREE CAVEATS, none of them small:

1. AMBIGUITY IS REAL AND SOME OF IT IS JUNK. 2,247 model codes map to more than one SoC. SM-S921U returning both QTI SM8650 and Qualcomm MSM8909 is not a regional variant — MSM8909 is a 2015 entry-level part and cannot be in an S24. So the catalog contains at least some bad rows, and a naive join will import them. Treat multi-valued results as unresolved rather than picking one, or you will hand the chipset lane confident wrong silicon. I have not characterised how many of the 2,247 are legitimate variants versus garbage; that needs doing before ingest.

2. VALUES ARE PLATFORM CODES, NOT MARKETING NAMES. 'QTI SM8650', 'Samsung s5e9945', 'Mediatek MT6769V/WY'. For CVE work I think that is better than 'Snapdragon 8 Gen 3', because Qualcomm and MediaTek bulletins are keyed by part number — but it is a different vocabulary from whatever gsmarena gave you, so the existing 147 chipset rows may not be directly comparable. Check before merging.

3. LICENCE. The mirror repo is Apache-2.0 but the DATA is Google's Play Console export, and the mirror's standing to redistribute it is untested. The clean path is exporting it from your own Play Console account: Monitor and improve -> Reach and devices -> Device catalog -> Export device list. Same file, unambiguous provenance. I would use the mirror to prove the pipeline and the first-party export for anything you keep.
