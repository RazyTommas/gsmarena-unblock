Fourth research lane in. This is the biggest one and it comes with a disclosure, so that first.

COMPLIANCE SLIP, MINE TO OWN. One of my research agents fetched a Pixel OTA package from dl.google.com whose robots.txt is 'Disallow: /'. It was a single one-off request to prove a technique, it self-reported the violation, and it did not crawl. But it should not have happened and I am telling you rather than letting it sit in a footnote. Nothing from dl.google.com should go into the pipeline, and Pixel must be sourced from the build-numbers page instead, which is explicitly permitted. No block was bypassed and no auth was touched anywhere in the research; this was a robots violation, not an access-control one. I have no way to un-fetch it. Flagging it so you can decide whether it taints the Pixel lane for you.

THE TECHNIQUE, which is the actual finding. OTA zips carry a plaintext metadata entry near the START of the archive, so an HTTP RANGE request of 32KB to 2MB reads the patch level without downloading a multi-gigabyte file:
  AOSP/Xiaomi/Google:  META-INF/com/android/metadata -> post-security-patch-level=2026-07-01
  BBK/OPlus (realme):  same entry ->  google_patch=20210805
That reframes 'the data is only inside the ZIP' from a dead end into a cheap fetch. It is the same reframe as doc.samsungmobile.com: the data was never unreachable, we were reaching for it wrong.

I VERIFIED TWO SOURCES MYSELF rather than take the agent's word:

THE TRAP IS LIVE IN THE HMD DATA AND WORTH SEEING. The same JSON object carries both:
  androidBulletinDate      2,872x day-01, zero scatter   <- the real ASPL
  dateOfFirstLiveRelease   flat scatter (28:149, 22:146, 24:120)  <- a release date
Pick the wrong key and you get a full, plausible, entirely wrong patch column. Same shape as mifirm. The day-of-month check catches it in one line, which is now three for three.

SOLVED, VERIFIED: Xiaomi/Redmi/POCO 197 devices (40/40 day-01), Pixel 48 (98.7% on day 01/05), HMD 87-102, TECNO 196, plus iQOO, OnePlus and vivo via community threads. Order of 550-600 devices of new coverage.

THE DECISION YOU MUST MAKE BEFORE INGESTING ANY OF IT: six of the nine solvable vendors publish only a patch MONTH, not a full date. If your schema demands 2026-08-05 they all fail; if it accepts 2026-08 they pass. That single modeling choice decides several hundred verdicts. I would model it as an explicit precision tier — date vs month — rather than padding months to -01, because padding invents a day the vendor never stated and it will read as a real ASPL forever after.

THREE CAVEATS I WOULD NOT INGEST WITHOUT:
  iQOO/OnePlus/vivo threads are COMMUNITY posts. The iQOO one is authored by an 'iQOO Ranger' community member, not the official account. Treat as unofficial and mark provenance per row.
  OnePlus threads server-render only for crawler user agents; a normal UA gets a 10.6KB SPA shell. Nothing was bypassed, but scale depends on that path and that is fragile.
  Pixel's 'build-ID embedded date == SPL' heuristic is only 65% exact (299/460). Do not use it. AD1A.240530.030 maps to 2024-07-05.
