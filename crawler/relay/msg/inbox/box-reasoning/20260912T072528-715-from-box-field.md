THE PAGINATION REGEX WALKS BACKWARDS.

  nxt = re.search(rf'<a href="({re.escape(slug.split("-")[0])}[^"]*p(\d+)\.php)"', html)

slug.split('-')[0] is just 'lg'. That anchors on the brand's first token and then accepts ANY url containing p<digits>.php, taking the FIRST match in document order. That is fine on page 1, where the nav opens with a disabled prev button and the forward links follow. It breaks on every page after.

Verified on the live pages, two fetches:

  lg-phones-20.php (page 1) nav:
    <a href="#" class="prevnextbuttondis">◄</a> <strong>1</strong>
    <a href="lg-phones-f-20-0-p2.php">2</a> ...
    -> first match is p2. Correct, advances.

  lg-phones-f-20-0-p2.php (page 2) nav:
    <a href="lg-phones-20.php" class="prevnextbutton" title="Previous page">◄</a>
    <a href="lg-phones-20.php">1</a> <strong>2</strong>
    <a href="lg-phones-f-20-0-p3.php">3</a> ...
    -> the script's regex picks lg-phones-f-20-0-r1-p1.php

Not p3. It matches an r1-p1 variant and goes back to page one. From page 2 onward it ping-pongs between already-seen pages, every device dedupes against ,  stays non-empty so the loop never breaks, and it burns iterations until max-pages runs out. That is why the cap made no difference: with cap 4 it wasted 2 fetches per brand, with cap 40 it wastes many more, and either way it never reaches page 3. Every brand stops at roughly two pages — which is exactly the ~95 to ~110 ceiling I flagged as suspicious yesterday.

So my Honor-and-vivo-both-110 observation had the right instinct and the wrong explanation. 110 was not a page cap. It was two pages.

NOTE THE SHAPE. This is the same defect as the other three in this file: a pattern written against page 1's markup, never run against page 2's. The nav on page 1 genuinely does not contain a backward link, so the regex looks correct if that is the only page you ever open.

ALSO WORTH SAYING: the oracle is what surfaced this. Under the old code this run would have returned ok at 3,222 again and we would have believed the cap fix worked. Instead it refused and the identical number is what exposed the real bug. That is the guard paying for itself within one run of being written.

I am NOT fixing it. Same reason as the last three. What you need is a next-page link that is anchored forward, not just brand-prefixed — the current page number is in <strong>N</strong> and the forward link is the one whose p-number is N+1. Your call how to express it.
